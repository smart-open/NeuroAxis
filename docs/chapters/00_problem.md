# 0. 这份文档解决什么问题


**一句话定位：一个"从工艺描述到可运行 PLC 程序"的 AI 工程 Agent——它读需求、写程序、在虚拟设备上把程序跑通、自己找出错在哪并修好，最后交出人和测试证据，人才把程序下到真机。**

### 0.1 为什么现在做（三个现实）

1. **PLC 编程是瓶颈而非壁垒**：中小集成商一台设备 1~2 周编程调试，其中 60% 时间在做"标准件"——启停互锁、气缸时序、报警、手自动切换。这部分有明确的模式，可被生成。
2. **虚拟调试已是行业惯例**：西门子 PLCSIM、CODESYS Control Win、倍福 TC/Target 都有免费或低成本仿真运行时，"先仿真跑通再碰硬件"不需要说服客户。
3. **LLM 生成工业代码的最大障碍不是"写不出"，而是"不敢用"**：梯形图/ST 写错会撞坏设备。所以产品的核心竞争力不是生成能力，而是**验证能力**——仿真台 + 静态检查 + 证据链。这决定了架构：先建测试台，再接 LLM。

### 0.2 用户与两个付费场景

| 用户 | 痛点 | 愿意付钱的原因 |
|---|---|---|
| 小型自动化集成商（1~10 人） | 项目排队，编程人手不够 | 标准逻辑生成 + 仿真预调试，把 2 周现场调试压到 1 周 |
| 设备制造商（OEM） | 每台设备按配置出程序，改来改去 | 规格驱动生成：选配变化只改 Spec，程序重生成，测试回归自动跑 |
| 工厂电气工程师（自维护） | 看不懂老程序、不敢改 | 程序→Spec 反向解析 + 仿真验证后再下载 |

### 0.3 产品形态（一个平台，P0 五大能力）

**灵枢 NeuroAxis 是一个工业智能开发平台**，前期（P0）围绕 PLC 开发全流程提供五大能力：

| # | 能力 | 说明 |
|---|---|---|
| 1 | PLC 程序开发 | Spec（工艺规格）→ IR → ST 确定性生成，人审 Spec 与 Diff，不审聊天记录 |
| 2 | 模拟调试 | 确定性软 PLC + 虚拟设备库（30+ 种元件，覆盖市面常见设备）+ 测试 DSL，仿真台即测试台 |
| 3 | 验证与门禁 | 静态检查 40 条 + 五道自动闸门（编译/静态/仿真/覆盖/变异），证据包留痕 |
| 4 | 知识库 | 厂商手册/规范/历史工程三层语料 RAG，检索必带引用，回答可溯源 |
| 5 | 错误排查与验证 | 仿真失败 → trace 归因（8 条规则 + LLM）→ Spec 修改提案 → 全量回归，≤5 轮收敛 |

### 0.3a 交付形态

| 形态 | 载体 | 用途 |
|---|---|---|
| Web 工作台 | Vue 3 前端 + FastAPI（浏览器访问） | 工程师日常：写 Spec、看生成、盯仿真、审批下载、知识库问答、错误排查 |
| 无头 CLI | `plcagent` Python CLI | CI/回归：`plcagent verify --project p1 --baseline golden` |
| 服务端 | FastAPI + LangGraph + PostgreSQL（P0 即启用） | 工程库、审批留痕、知识库；多人协作与权限隔离 P1 细化 |

**P0 只做 Web + CLI**（同进程托管，数据落 PG）——浏览器直接用，不装客户端；多人协作与权限隔离 P1 再细化。

### 0.4 与 13 号平台的关系（不重复造轮子）

本产品定位为 13 号平台的一个**能力插件**（`kind: Copilot`），复用其：设备驱动插件（02 号驱动契约）、RBAC/审计、日志体系（客户端复用点由 Web 工作台承接）。本产品自己新增的内核只有四块：

```
[Spec/IR 引擎] [ST 生成与检查] [仿真台(软PLC+虚拟设备)] [Agent 编排]
```

所以本文档只详设这四块 + 它们对 13 号契约的挂接点；登录、权限码、审计哈希链等直接引用 13 号 9 章的结论，不重写。
